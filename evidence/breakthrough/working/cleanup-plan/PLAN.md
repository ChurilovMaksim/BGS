# План чистки BGS до состояния публичного научного репозитория

**Статус этого документа.** Это только план. Он ничего не меняет
в репозитории: нет пушей в `main`, нет удалений, нет перемещений файлов.
Файл лежит вне репозитория — в рабочей папке
`bgs-breakthrough/cleanup-plan/` — именно чтобы подготовка чистки
не засоряла сам репозиторий.

**Дата и основание.** 1 ноября 2026. Изучены: локальный снимок
`formalization/` от 29 октября (README, `Bgs.lean`, `Bgs/`,
`drafts/`, `MATHLIB_LAYER_RU.md`, `seven_primary_certificate.md`)
и, для сверки, копия дерева HEAD `0d1bf5891e60` (`bgs-full-head-0d1b`).
Вывод сверки важен и честен: **снимок от 29 октября устарел**.
В нём `Bgs/` — 49 файлов верхнего уровня + 39 в `Bgs/Mathlib/`,
а в копии HEAD `0d1b` — уже 116 файлов верхнего уровня + 39 в
`Bgs/Mathlib/`, включая серии `LineB…LineN` и `LineE`.
Поэтому все числа ниже — это то, что проверено в этих двух копиях,
а не канонический счётчик репозитории. Перед любым перемещением
инвентаризацию надо повторить по актуальному HEAD (см. фазу 0).
**Уточнение по HEAD:** на старте 5-дневной программы прорыва
зафиксирован HEAD `a562e0cf` (PR #74) — новее, чем проверенная
здесь копия `0d1b`. Фаза 0 обязана инвентаризовать именно
актуальный HEAD на момент исполнения (не `0d1b` и тем более
не снимок от 29 октября); цифры из `0d1b` ниже — только
иллюстрация роста дерева, а не база для перемещений.
Источником истины о составе формализации считается граф импортов
`Bgs.lean` + `Bgs/Mathlib.lean`, а не просто список файлов в папке:
файл вне графа импортов — кандидат в архив, а не «молчаливый»
участник сборки.

**Параллельный агент.** Прямо сейчас другой агент делает Line E
в `main`. Этот план построен так, чтобы ему не мешать:
до его посадки — только чтение и черновики вне репозитория
(фаза 0–1). Никаких правок `Bgs.lean`, `claims.json` и файлов
`Line*` до сигнала о посадке Line E.

## 0. Принципы: что значит «не стыдно показать»

Публичный научный репозиторий читается так: человек, впервые
открывший его, за 10 минут понимает

1. что такое гипотеза BGS и что именно здесь утверждается;
2. что **доказано** (и чем именно — Lean, численно, аналитически),
   что **сформулировано, но открыто**, а что — **только конечный
   частный случай или ядро**;
3. как это перепроверить одной командой, без доверия на слово.

Отсюда три жёстких правила, которые действуют на весь план:

- **Никакого повышения статуса.** Конечный сертификат, ядро,
  фрагмент и формулировка утверждения — это не доказательство
  общей теоремы. Слова «доказано», «proved», «закрыто» в `main`
  допустимы только в смысле раздела 3.
- **Каждый файл трассируется.** У Lean-модуля есть Claim ID,
  человеческий заголовок и ссылка на математический документ
  или на запись о пробеле. Файл без трассировки — не «мелочь»,
  а дефект, который чинится заголовком или уходом в архив.
- **Машинные дампы — в `evidence/`, а не в текст для людей.**
  Длинные таблицы из сотен имён теорем, логи сборок, хеши и
  перечни jobs — это приложения и квитанции, а не основной текст.
  Основной текст пишется предложениями, для человека.

## 1. Предлагаемое чистое дерево репозитория

Дерево ниже — целевое состояние корня репозитория. Оно не
выдумывает новые разделы с нуля: оно закрепляет разделы, которые
в репозитории уже есть (`formalization/`, `mathematics/`,
`evidence/`, `archive/`, `computations/`), и убирает из `main`
всё, что является рабочим мусором.

```text
/
├── README.md                     # одна человеческая страница: что это,
│                                 # что доказано / открыто, как проверить
├── CONTRIBUTING.md               # коротко: ворота из раздела 3, как предлагать пакет
├── formalization/                # ТОЛЬКО то, что собирается и проверяется
│   ├── README.md                 # короткая человеческая версия (см. раздел 4)
│   ├── MATHLIB_LAYER.md          # см. раздел 4: сохранить имя файла на первом проходе,
│   │                             # переписать введение и сводку; таблицу деклараций
│   │                             # держать как приложение, а не как основной текст
│   ├── seven_primary_certificate.md  # короткая квитанция, а не пересказ кода
│   ├── lakefile.toml
│   ├── lean-toolchain            # Lean 4.33.1 / Mathlib v4.33.1, без изменений без причины
│   ├── lake-manifest.json
│   ├── Bgs.lean                  # единственный корневой агрегатор; импорты —
│   │                             # алфавитные внутри смысловых групп, без пустых
│   │                             # «исторических» разрывов (см. замечание ниже)
│   ├── Bgs/
│   │   ├── <ядра и сертификаты>  # плоская структура сохраняется на первом проходе:
│   │   │                         # переименование модулей ломает все импорты,
│   │   │                         # поэтому НЕ переименовывать ради «красоты»
│   │   ├── Mathlib.lean          # агрегатор слоя Mathlib
│   │   └── Mathlib/              # 39 адаптированных модулей, без второго проекта
│   └── drafts/                   # УДАЛЯЕТСЯ как раздел main: черновики живут
│                                 # только в archive/drafts/ (см. раздел 2)
├── mathematics/                  # человеческие математические документы, по одному
│   ├── fixed-map/                # предмету/claim'у; каждый документ называет
│   ├── trace-bridge/             # гипотезы, пробелы и то, что НЕ доказано
│   ├── cayley-arithmetic/
│   ├── open_questions.md         # единый список открытого, без дублей
│   └── ...                       # (точный перечень — по инвентаризации фазы 0)
├── computations/                 # проверяющие программы, а не «доказательства»
│   ├── verification/             # Python-проверки, на которые ссылаются Lean-заголовки
│   ├── cpp/                      # C++-верификаторы (там, где они реально есть)
│   └── maintenance/              # только реально нужный shim/адаптер, с объяснением
│                                 # зачем он нужен; мёртвые адаптеры — в архив
├── evidence/                     # квитанции, а не утверждения
│   ├── formalization/            # датированные build receipts, axiom-логи, blob SHA
│   ├── executions/               # датированные логи запусков, по одному на запуск
│   └── numerics/                 # выходы численных проверок (если они отделены
│                                 # от computations/verification/)
├── archive/                      # история, которую жалко терять, но стыдно
│   ├── record/                   # старые аудиты, integration dispositions
│   ├── evidence/                 # superseded receipts и старые логи
│   └── drafts/                   # не вошедшие в граф черновики (см. раздел 2)
├── record/
│   └── claims.json               # реестр утверждений — единственный источник
│                                 # статусов; статусы в prose-документах обязаны
│                                 # совпадать с ним, а не жить своей жизнью
└── .gitignore                    # .lake/, oleans, локальные build-деревья,
                                  # тестовые копии — никогда не коммитятся
```

**Что в этом дереве намеренно НЕ делается на первом проходе:**

- Не переименовываются Lean-модули и не меняется структура
  `Bgs/` ради эстетики. Любое перемещение Lean-файла — это
  одновременное изменение `Bgs.lean`/`Bgs/Mathlib.lean` в том же
  пакете, иначе сборка падает. Красота имён — задача второго
  прохода, после зелёной сборки.
- Не создаётся второй Lake-проект и не дублируется дерево
  доказательств. Один корень — `formalization/`, один агрегатор —
  `Bgs.lean`.
- Не заводится `staging/` в `main`. Рабочие черновики, тестовые
  копии (`bgs-test-*`, `*-TEST COPY ONLY*`) и промежуточные
  пакеты живут вне репозитория, в рабочей папке, и попадают
  в `main` только готовым пакетом. Пример мусора, который не
  должен попадать в коммит: файл вида `Bgs.lean.old-tree`,
  замеченный в локальной build-копии HEAD `0d1b`.
- `.lake/` не является частью репозитория никогда: это локальный
  build-артефакт (в нём же лежат oleans Mathlib, гигабайты).
  Правило из локального опыта: один и тот же `formalization/.lake`
  переиспользуется между чекаутами, а не коммитится и не копируется.

**Замечание про `Bgs.lean`.** В снимке от 29 октября импорты
разбиты пустыми строками на «исторические» группы без объяснения,
почему группа именно такая. В целевом состоянии группы должны
быть смысловыми и подписанными комментариями
(ядра → рациональные свидетели → Mathlib-слой), либо файл
становится просто алфавитным списком. Перегруппировка — мелкая
правка, но только после посадки Line E и только вместе с
пересборкой: порядок импортов сам по себе не должен ничего
ломать, но проверять это надо сборкой, а не рассуждением.

## 2. Правило: что в архив, а что удаляется только через владельца

### 2.1. В `archive/` — без спора, но только после проверки, что это не единственная копия

| Категория | Примеры (проверены в снимках) | Куда |
|---|---|---|
| Не вошедшие в граф импортов черновики | `formalization/drafts/FiniteOrbitAlgebra20260922.lean` (34 строки, «source only», не typechecked), `drafts/JackArithmeticCore.lean` (помечен UNCOMPILED DRAFT), `drafts/TemporalCancellation.lean` | `archive/drafts/` с сохранением исходного заголовка о статусе |
| Тестовые копии модулей | любая копия с пометкой «TEST COPY ONLY», копии из `bgs-test-*` рабочих папок, если они случайно попали в `main` | `archive/drafts/` или удаление через владельца (см. 2.2), если это точный дубль уже вошедшего модуля |
| Поглощённые модули | бывший отдельный `CayleyExceptionalK23.lean`, свёрнутый в `CayleyEnergy.lean` (если его файл ещё где-то лежит) | `archive/` с запиской «folded into X, дата, коммит» |
| Устаревшие квитанции и логи | receipts 16-/17-/19-/20-модульных сборок, когда есть актуальный агрегат; старые `aggregate-build.json` после нового полного прогона | `archive/evidence/` — не удалять молча: старый receipt может быть единственной квитанцией за старый модуль |
| Старые аудиты и dispositions | `archive/record/*` — уже в архиве; не «чистить» архив ради чистоты | остаются в `archive/record/`, на них ссылаются, их не переписывают |
| Служебные файлы, не относящиеся к науке | `Bgs.lean.old-tree`, локальные адаптеры, потерявшие актуальность | `archive/` (адаптер) или удаление через владельца (мусор вида `*.old-tree`) |

Перед перемещением каждого файла — три проверки, все три
обязательны: (а) файл не входит в граф импортов актуального
`Bgs.lean`/`Bgs/Mathlib.lean`; (б) на него нет ссылок из
`claims.json` и из заголовков живых модулей; (в) его содержимое
сохранено в архиве целиком (сверка по blob SHA до и после),
а не «примерно перенесено».

### 2.2. Только через владельца (отдельный PR, отдельное разрешение) — никогда молча и никогда через коннектор

Удалению подлежат только файлы из этого списка, и каждое удаление
— отдельной строкой в заявке владельцу, с причиной:

1. Точный дубль уже вошедшего в `main` модуля (совпадение по blob
   SHA, а не «похоже»).
2. Файл, который является единственной копией доказательства,
   квитанции или математического документа, — **не удаляется
   вообще**, пока его содержимое не перенесено в живой файл
   и не сверено.
3. Любой файл, на который ссылается `claims.json`, внешний
   документ или опубликованная ссылка.
4. Любой файл из активного графа импортов без замены в том же
   пакете.
5. Любой файл, чьё удаление меняет статус claim'а в реестре
   (например, убирает единственного verifier'а).

**Открытый пункт — ограничение инструментов (зафиксировано,
а не обойдено).** Через GitHub-коннектор **нельзя удалить файл**
и **нельзя сделать поиск по всему репозиторию**. Поэтому:

- этот план не предлагает «обходного пути» через коннектор;
- все перемещения и удаления из разделов 2.1–2.2 маршрутизируются
  **другому агенту / владельцу** с правами git-доступа, отдельным
  PR, после посадки Line E;
- в handoff тому агенту должны уйти: точный список путей
  (старый → новый), blob SHA каждого файла до перемещения,
  подтверждение проверок (а)–(в) из 2.1 и пометка, что именно
  требует решения владельца из списка 2.2;
- пока этот PR не влит, файлы остаются на месте. «Чистка»,
  которая потеряла файл, хуже, чем грязный репозиторий.

### 2.3. Что НЕ архивируется и НЕ удаляется под видом чистки

- **Фальсификаторы и регрессионные стражи.** Пример:
  `Bgs/HistoricalMobiusDegenerateFiber.lean` — это не «старый
  мусор», а явный контрпример к отозванному маршруту (вырожденный
  слой `d = 0`, конечные сертификаты при `p = 53` и `p = 199`).
  Такие файлы остаются в формализации, с заголовком «falsifier /
  regression guard», а не уезжают в архив как «исторические».
- **Statement-only модули.** `TraceStatement`, `Fm001Statement`,
  `Fm021Statement` — это формулировки открытых утверждений,
  а не недоделки. Они остаются в `main` только с честной
  пометкой STATEMENT ONLY (см. раздел 3). Убирать их «за
  отсутствие теорем» — значит прятать открытые проблемы.
- **Конечные ядра и фрагменты.** `SevenPrimary`, `FourCutKernel`,
  рациональные свидетели `*Rational.lean`, `LineN*Arith` —
  это не «мелкая арифметика, которую стыдно показывать»,
  а ровно то, что формализовано. Стыдно — только выдавать их
  за большее. Лечатся заголовком и разделом 3, а не удалением.

## 3. Жёсткие ворота: что может попасть в `main`

Любой файл, претендующий на `main`, проходит все ворота.
Одно невыполненное ворота — файл не вливается, независимо от
того, «как красиво» он выглядит. Проверки — механические там,
где это возможно, а не «на глаз».

### 3.1. Ворота для Lean-модулей

| № | Ворота | Как проверяется | При провале |
|---|---|---|---|
| G1 | `lake build Bgs` завершается с `EXIT:0` | Полная сборка после пакета, **последовательно** для модулей с `import Mathlib` (см. 5.3: параллельный прогон таких модулей на этой ВМ не сходится — page-cache thrash) | Пакет не вливается; чинится, а не «вливается с надеждой на CI» |
| G2 | Только стандартные аксиомы | `#print axioms` для всех публичных теорем: допустимы только `propext`, `Classical.choice`, `Quot.sound` или их отсутствие | Любая нестандартная аксиома — стоп, с явным указанием теоремы |
| G3 | `sorry` в коде — 0 | Поиск по коду, а не по комментариям: упоминание слова `sorry` в комментарии («no sorry here») — не нарушение, но и не доказательство; настоящий `sorry`/`admit` в теле доказательства — провал. Отдельно запрещена команда `axiom` | Провал без обсуждений |
| G4 | `native_decide` / `decide` — только с раскрытием доверия | В заголовке модуля явно сказано: что решается вычислением, что при этом доверяется (нативная компиляция/вычисление), и есть ли независимый replay. Kernel-`decide` предпочтительнее `native_decide`. Модули с `native_decide` (в снимке от 29 октября — 16 файлов верхнего уровня, включая `SevenPrimary`, `CayleyEnergy`, `FourCutKernel`, `PellCoboundary`) не получают статус «обычного доказательства» без этой пометки | Без пометки о доверии — не вливается |
| G5 | Численная проверка, где применимо | Если модуль — конечный сертификат или рациональный свидетель, рядом должен быть независимый проверяющий путь (Python и/или C++ из `computations/`, либо явная запись, почему независимого пути нет и что вместо него). Lean-`decide` внутри того же модуля независимой проверкой не считается | Нет независимого пути и нет честной записи — не вливается |
| G6 | Человеческий заголовок (шаблон — в приложении А) | В начале файла, предложениями: что доказывается, при каких гипотезах, что НЕ доказывается, Claim ID, ссылка на математический документ и на квитанцию | Машинный заголовок («сертификат для…», перечень без гипотез) — возвращается на переписывание |
| G7 | Нет битых ссылок и устаревших чисел | Все относительные ссылки (`../evidence/…`, `../mathematics/…`, `../archive/…`) ведут на существующие файлы; все числа (jobs, даты, счётчики теорем) сверены с актуальной квитанцией, а не скопированы из старой | Битая ссылка или число «из прошлого» — провал, чинится до влития |
| G8 | Нет следов рабочего процесса | Нет пометок «TEST COPY ONLY», «UNCOMPILED DRAFT», «source only», временных имён, закомментированных кусков кода без объяснения | Возвращается на чистку |

### 3.2. Ворота для prose-документов (README, математика, квитанции)

- Документ называет свой статус в первом абзаце: что это —
  доказательство, формулировка, ядро, сертификат, квитанция
  или архивная запись.
- Статус claim'а в документе совпадает с `claims.json`.
  Расхождение — дефект документа, а не «другая точка зрения».
- Нет утверждений вида «доказано», если доказана только часть:
  пишется «доказано: …; не доказано: …; открыто: …».
- Открытые утверждения (BGS-BGS-001 — сама гипотеза BGS,
  BGS-TRACE-005 и др.) никогда не переходят в разряд доказанных
  из-за соседства с доказанными леммами.
- Квитанция (receipt) содержит: команду, коммит/базу, дату,
  `EXIT`-код, число jobs, результат axiom-аудита и blob SHA
  проверенных файлов. Квитанция без команды и без SHA —
  не квитанция, а воспоминание.

### 3.3. Статусные ярлыки — единственные допустимые

Каждый Lean-модуль и каждый математический документ носит
ровно один ярлык (в заголовке, первой строкой после названия):

- `PROVED` — только при G1–G8 и при полном соответствии
  формулировки claim'а (не его частного случая).
- `KERNEL / FRAGMENT` — доказана часть, ядро или лемма;
  в заголовке перечислено, что именно, и что осталось.
- `FINITE INSTANCE` — доказано только при явных параметрах
  (например, `(p, K, a) = (53, 13, 10)` или `p = 7, K = 3`);
  обобщение НЕ утверждается.
- `STATEMENT ONLY` — только определения и `Prop`ы, теорем нет,
  claim открыт (примеры: `Fm001Statement`, `Fm021Statement`,
  `TraceStatement`).
- `FALSIFIER` — контрпример / регрессионный страж; положительный
  результат не утверждается.
- `OPEN` — для математических документов об открытых проблемах;
  в Lean такому документу соответствует либо STATEMENT ONLY,
  либо отсутствие модуля.

Модуль без ярлыка в `main` не допускается. Переход ярлыка
вверх (например, `FINITE INSTANCE → PROVED`) — только новым
пакетом с новой квитанцией, а не правкой заголовка.

### 5.3. Технические ограничения сборок (локальный опыт, не теория)

- Модули с `import Mathlib` собираются **последовательно**.
  Параллельный прогон таких модулей на этой ВМ (7.7 GiB RAM,
  oleans Mathlib ~6 GB) приводит к thrash page cache
  (~30 GB чтений на модуль, ~3% CPU) и не сходится.
  Это ограничение планировщика чисток, а не повод уменьшать
  ворота G1.
- Холодный page cache после перезагрузки ВМ делает первый
  Mathlib-модуль очень долгим (наблюдалось 33+ минут).
  Планировать сборки с запасом, а не «быстро перед влитием».
- `lake exe cache get` — один раз на окружение (или после
  смены pin'а Mathlib); `formalization/.lake` переиспользуется,
  а не пересоздаётся на каждый пакет.

## Приложение А. Шаблон человеческого заголовка Lean-модуля

Копируется в начало файла как Lean-комментарий (`/-! … -/`),
первым содержательным блоком файла. Технические `set_option`
ставятся после заголовка, кроме редких случаев, когда опция
нужна для самого парсинга заголовка, — тогда это явно
помечается в заголовке. Шаблон:

```lean
/-!
# <Название модуля> — <ярлык из 3.3: PROVED / KERNEL / FINITE INSTANCE / STATEMENT ONLY / FALSIFIER>

Что доказывается (одним-двумя предложениями, без формул-кода):
  …

Гипотезы:
  - …
  - …

Что НЕ доказывается / что остаётся открытым:
  - …
  - …

Claim: <BGS-… ID> — статус в claims.json: <…>
Математический документ: <путь в mathematics/…>
Численная проверка: <путь в computations/… или «не применимо, потому что …»>
Доверие: <обычные доказательства / kernel decide / native_decide + независимый replay: …>
-/
```

Пример хорошего заголовка, уже существующего в репозитории
(образец, а не идеал): `TraceStatement` — формулировка,
открытость и ссылки названы прямо. Пример плохого заголовка:
однострочный «finite kernel only» без claim'а, гипотез
и пробелов — такой заголовок возвращается на переписывание
по воротам G6, даже если код модуля безупречен.

## Приложение Б. Контрольный grep-набор для ворот G3–G4, G8

Выполняется на дереве `formalization/` перед каждым пакетом
(не заменяет сборку и axiom-аудит, а дополняет их):

```sh
cd formalization
# настоящий sorry/admit в коде (комментарии со словом sorry сюда не попадают
# только если они не содержат кода; ручная проверка совпадений обязательна)
grep -rn --include='*.lean' -E '\bsorry\b|\badmit\b' Bgs/ Bgs.lean
# новые аксиомы
grep -rn --include='*.lean' -E '^\s*axiom ' Bgs/ Bgs.lean
# native_decide — сверить с пометками о доверии в заголовках
grep -rln 'native_decide' Bgs/
# следы рабочего процесса
grep -rn --include='*.lean' -E 'TEST COPY ONLY|UNCOMPILED DRAFT|source only' Bgs/ Bgs.lean
# файлы вне графа импортов (сравнить с импортами Bgs.lean + Bgs/Mathlib.lean)
```

Любое совпадение разбирается вручную: grep — это сигнал,
а не приговор. Особенно важно не перепутать упоминание
`sorry` в комментарии («no sorry») с настоящим `sorry`
в доказательстве — в снимке от 29 октября единственное
«совпадение» такого рода было именно комментарием
в `drafts/FiniteOrbitAlgebra20260922.lean`.
