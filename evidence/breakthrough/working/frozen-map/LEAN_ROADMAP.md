замыкание агрегатора. И наоборот: успешный `lake build Bgs` ничего не
говорит о файле-сироте. Поэтому каждая стадия ниже проходит ДВА режима:

## 3. Порядок следующих целей — от уже пересобранного к открытому

Общий принцип порядка: каждый следующий модуль импортирует только
прямых предшественников и одну новую идею. Модуль, в котором
смешаны новая идея и её применение, делится. Модуль с гипотезой
внутри называется условным, а не доказанным, и в main идёт только
с явной пометкой условности (если вообще идёт — см. §6).

### Стадия 2. hEquidistUnits — первая цель, самая близкая к закрытию

Зависимости: `LineBNAverageUnits` (таргет и зеркало `nAverageTup_units`),
`LineBTraceM1`/`LineBHfib` (полный блок), леммы об окне из стадии 3
(частично, для члена `D/X`).

Разбить минимум на три модуля, а не один большой:

1. `...UnitsBlock` — неполные блоки: член `D/X` от хвоста окна.
   Чисто счётная лемма о числе полных блоков и остатке; никаких
   средних, никаких `decide` по окну (окно неограниченно по `X`).
2. `...UnitsEquidist` — равномерность `ν_N` по единицам
   `(ZMod g')ˣ` на полных блоках. Это содержательное ядро стадии;
   здесь сначала обязательна численная проверка вне Lean
   (Python/C++ по дизайну из ветки numerics), и только потом Lean.
   Если численный тест даёт контрпример — стадия останавливается,
   формулировка меняется, контрпример фиксируется отдельным
   модулем-опровержением по образцу `LineD150HcollapseFalse`,
   а не «чинится» подгонкой константы.
3. `...UnitsAssembly` — сборка: `nAverageTup_units` минус гипотеза
   `hEquidistUnits` плюс блоки 1–2 даёт безусловную (или с точно
   названным остатком) теорему среднего по единицам.
   Отдельно в шапке: точная константа. Расхождение ≈ `2π`
   между первым членом ошибки и границей 175 — самостоятельная
   подзадача, а не «мелочь»: либо константа улучшается леммой,
   либо граница 175 переформулируется с честным первым членом.
   Скрывать расхождение округлением нельзя.

Ожидаемые трудности: API единиц `ZMod` и `Nat.totient` (нормировка
`1/φ(g')` при `g' = 1, 2` — краевые случаи отдельно, как в Units);
суммирование по `(ZMod g')ˣ` при переменном `g'`; перенос
равномерности с полных блоков на окно с хвостом без потери
константы. Обход: структурные леммы о разбиении окна на блоки
вместо `decide`/`Finset` перебора по `N`.

Критерий выхода со стадии: `nAverageTup_units` без гипотезы
`hEquidistUnits` либо с остатком, у которого названы все члены,
и отдельный пересчёт константы.

### Стадия 3. Окно (X, 2X] — инфраструктура, нужная стадиям 2 и 4

Зависимости: `LineBHfib` (полный блок `admBlock X D`,
`hfib_of_complete_block`, `admBlock_nonempty`), `LineBNAverageM1`
(леммы об окне при `m = 1` как образец).

Разбить на:

1. `...WindowMem` — принадлежность окну, взаимная простота
   `gcd(N, D) = 1`, постоянство вычета на окне в малых случаях
   (образец: `window_nu_eq_one` при `m = 1`).
2. `...WindowCount` — счёт окна: число полных блоков, хвост,
   оценка хвоста `D/X`. Только здесь появляется член `D/X`,
   и только отсюда он импортируется в стадию 2 — не наоборот,
   чтобы не было циклических импортов.
3. `...WindowUnits` (по мере нужды) — ограничение окна на единицы:
   какие `N` окна дают вычет-единицу, как хвост окна искажает
   равномерность.

Ожидаемые трудности: окно задано вещественным `X`, а счёт —
целочисленный; смешение `ℝ`/`ℕ` — главный источник «почти верных»
лемм. Обход: все леммы о принадлежности окна формулировать
сначала в `ℕ` (целая часть, интервалы `Finset.Ioc`), и только
потом переносить на `ℝ`-окно. `decide` по окну запрещён:
окно зависит от параметра `X` и не является конечным фиксированным
объектом.

Критерий выхода: лемма о хвосте окна с явной константой `D/X`,
готовая к импорту в сборку стадии 2.

### Стадия 4. kickMatInf — самая аналитическая цель, первой идёт интерфейсная стадия

Зависимости: следовая формула (`LineBTraceFormula`, `LineBTsum`,
`LineBGauss`, `LineBExpand`), `LineBDerand`, ветка D (фаза).

Порядок внутри стадии — обратный наивному:

1. Сначала интерфейсный модуль `...KickMatInfInterface`: точная
   формулировка отождествления конечной kick-матрицы с бесконечной
   (`kickMatInf`) КАК ГИПОТЕЗА с именем, областью и списком того,
   что из неё следует (в частности, какие теоремы 163/175 она
   закрывает). Модуль помечается `conditional`/`interface`,
   в реестр claims — только как условный, никогда как доказанный.
2. Потом — леммы о предельном переходе по одному параметру за раз:
   сходимость следов, устойчивость гауссова шага, перенос
   фазовой леммы с `PsiMode` на след. Каждая лемма — отдельный
   файл, если её доказательство использует новый аналитический
   приём (суммируемость, перестановка сумм, оценка хвоста).
3. Только потом — попытка снять гипотезу интерфейса. Если
   аналитический вход (например, равномерная оценка следа)
   в дереве отсутствует, стадия останавливается на интерфейсе:
   это честный результат, а не провал. Подмена интерфейса
   конечным игрушечным оператором запрещена тем же аргументом,
   что и в шапке 149Props: игрушка удовлетворит гипотезу
   тривиально, но не закроет её для настоящего оператора.

Ожидаемые трудности: бесконечные суммы (`tsum`) и перестановка
пределов; `kickMatInf` — это предельный объект, и любая лемма
«конечное = бесконечное» без оценки хвоста ложна по построению.
Обход: сначала оценка хвоста с явной константой, потом равенство
пределов; никогда наоборот.

Критерий выхода: либо снятая гипотеза интерфейса с полным
аудитом, либо интерфейс с точным списком недостающих аналитических
лемм. Промежуточного статуса «почти доказано» нет.

### Стадия 5. J0-ансамбль — сначала извлечение определения, потом Lean

J0 упоминается в памяти проекта как остаток для 152-full, но
в изученных тестовых копиях его определение не встречается
(в `bgs-test-175units` есть `LineDStrongKickConc`, но не J0-модуль).
Поэтому первая подстадия — не Lean, а источниковедение:

1. Выписать определение J0-объекта дословно из источника
   (какой ансамбль, какая функция Бесселя `J0`, где нормировка),
   с указанием файла и раздела источника. Без этой выписки
   модуль не начинается: нельзя формализовать объект, чьё
   определение не зафиксировано.
2. Конечномодовая аппроксимация: J0 как предел конечномодовых
   сумм, оценка аппроксимации — отдельно от предельного перехода.
3. Связка с `LineDStrongKickConc` (ω-затухание G-ансамбля,
   Γ-инвариантность `modeSum`): какие леммы StrongKickConc
   переиспользуются дословно, а какие требуют J0-веса.

Ожидаемые трудности: специальные функции в Mathlib (`Bessel`),
сходимость по модам, отличие J0-веса от гауссова веса в 152.
Обход: аппроксимацию и предел — разными модулями; `decide`
по функциям Бесселя невозможен в принципе, здесь только анализ.

Критерий выхода: либо J0-теорема с явной оценкой аппроксимации,
либо зафиксированное определение + список недостающих лемм.

  точная константа. Пока хоть один из этих пунктов открыт,
  статус — `conditional`.
- 152-full: StrongKickConc + hSep в общем виде + J0 (стадия 5) +
  N-шаг через фазовую замену (не через ложный `hcollapse`) +
  тождество `Fix m` с тором `Fix_m` (отдельная подзадача,
  не входящая в стадии 2–5).

Правило сборки: claim помечается закрытым только тогда, когда
все его гипотезы сняты модулями с полным аудитом (§6). Один
открытый пункт — и весь claim остаётся условным, без частичных
процентов «доказанности».

## 4. Протокол сборки на этой ВМ (обязательный, без исключений)

1. Новая рабочая копия — только в `~/workspace/`, никогда в `/tmp`
   (см. §0). Имя копии отражает стадию и дату, например
   `bgs-test-175equidist-202611xx`, а не общее `bgs-test-new`.
2. Скопировать пин (`lean-toolchain`, `lakefile.toml`,
   `lake-manifest.json`) и `.lake` по правилу §0. Изменённые
   для теста файлы записать в журнал копии отдельной строкой.
3. Вычислить полное транзитивное замыкание импортов ДО сборки:
   рекурсивно по `^import` через агрегаторы, включая вложенные
   пути вида `Bgs.Mathlib.*`. Сверить: число недостающих модулей
   должно быть 0. Счёт только по верхнему уровню импортов —
   не доказательство (прямое требование skill).
4. Собрать зависимости целевого модуля по одной, в топологическом
   порядке, строго последовательно. Сначала `lake build` зависимости,
   потом аудит аксиом модуля: `lake env lean` НЕ создаёт olean'ы,
   и недостающий olean зависимости после такой проверки — это
   сбой окружения, а не результат (прямое предупреждение skill).
5. Каждый модуль с `import Mathlib` — отдельным запуском, без
   параллельных сборок. Полный `lake build Bgs` — только после
   того, как все его модули прошли поодиночке; агрегатор в полном
   дереве шёл ~730 с в прецеденте, полный прогон — 8859–8862 jobs,
   закладывать это время в план, а не «быструю проверку».
6. После перезагрузки ВМ или очистки: пересобрать копию с нуля
   и сравнить новый лог со спасённым, прежде чем переиспользовать
   старые результаты.
7. Во время долгой сборки — короткие статусы по завершённым шагам
   (что собралось, что следующее), а не молчание до конца.

## 5. Стратегия против decide / OOM

Прецеденты, из которых выведены правила:

- Kernel-`decide` для `det H_7` в проекте — невыполним (OOM).
  Повторять то же вычисление на большей машине без изменения
  математики — запрещено skill: вместо этого структурная лемма
  или разбиение модуля.
- `hSep [CA]`-шаг в Lean как `decide` невыполним, но независимый
  exact replay на чистом Python прошёл (таблица `m = 3..7`,
  плохих волокон 0). Replay — это verifier-артефакт, а не
  доказательство в Lean, и в реестр он так и записывается.

Правила:

- `decide` разрешён только на малых фиксированных конечных объектах:
  образец — PhaseLemma: `interval_cases m <;> decide` при
  `3 ≤ m ≤ 9` для таблиц `dOf`/`xm_entry_fin`/`e_eq_gp`
  (значения `d = 14, 24, 82, 140, 478, 816, 2786`).
  Граница диапазона — часть утверждения; расширение диапазона
  требует новой оценки стоимости, а не просто замены `9` на большее.
- `decide` запрещён: по матричным определителям нетривиального
  размера, по окну (параметр `X`), по бесконечным суммам,
  по функциям Бесселя, по любому объекту с параметром `m`
  без верхней границы.
- Вместо brute force — структурная лемма. Образец из PhaseLemma:
  `two_mul_Qform_dvd` доказывает `d ∣ 2Q(n)` линейностью
  по двойной сумме из делимости самих записей `d ∣ 2X_ij`,
  без спаривания и без перебора мод.
- Конечные инстансы (`m = 3`, `m = 6` и т.п.) — отдельные малые
  модули, а не леммы внутри общего доказательства: общий модуль
  не должен падать из-за одного тяжёлого инстанса.
- `native_decide` в основном коде — красный флаг: он не входит
  в стандартный набор аксиом молча, его вхождения считаются
  отдельно (см. §6), и для пуша требуется 0, если только
  конкретное вхождение не обосновано отдельно и не отражено
  в списке аксиом. Прецедент проекта: чистка legacy `native_decide`
  88 → 37 — это долг, а не норма.
- При OOM/таймауте: остановить, разбить модуль или доказать
  структурную лемму, пересчитать замыкание, пересобрать.
  Повтор того же запуска без изменений — не шаг, а потеря времени.

## 6. Чек-лист аудита аксиом перед любым пушем (все пункты — обязательно)

Выполняется на свежей базе: HEAD main перепроверяется через
GitHub-коннектор непосредственно перед пакетом (прецедент:
за день HEAD ушёл `0d1bf589 → a562e0cf`, PR #74; пакет,
подготовленный на старой базе, перебазируется, а не пушится).

- [ ] Лог полной пересборки пакета сохранён в файле в рабочем
  каталоге; в логе `EXIT:0` и нет оборванных/усечённых списков.
  Пустой вывод, усечённый лог или частичный список аксиом —
  это отсутствие результата, проверка повторяется до полного списка.
- [ ] Для КАЖДОЙ главной теоремы модуля прочитан полный вывод
  `#print axioms` из сохранённого лога (образец: PhaseLemma —
  `#print axioms` в конце файла для всех главных теорем;
  149Props — 6 строк; M1 — 15 строк; Units — 5 строк).
  Выборочная проверка «пары теорем» не допускается.
- [ ] Список аксиом — только стандартный набор
  (`propext`, `Classical.choice`, `Quot.sound` — точный состав
  сверяется с логом, а не с памятью). `sorryAx` = 0.
  Любая нестандартная аксиома — стоп, с именованием теоремы.
- [ ] Подсчитаны отдельно, с точным поиском, и равны 0 в коде:
  `sorry`, `admit`, `axiom` (объявление), `native_decide`.
  Совпадения в комментариях и шапках («No sorry…») НЕ считаются
  и отдельно помечаются как упоминания, а не вхождения:
  в изученных файлах `grep sorry` даёт ровно по 1 строке —
  и это строка шапки, а не код.
- [ ] Все места `by decide` перечислены с их границами
  (объект, диапазон, размер). Ни одного `decide` вне правил §5.
- [ ] Для каждой теоремы выписан точный список гипотез —
  именами из формулировки. Модуль с хоть одной оставшейся
  гипотезой помечен `not full` / `conditional`, и в реестр
  claims он вносится именно так, с гипотезами, а не как
  «доказано».
- [ ] Математический статус и формализационный статус разделены
  в шапке и в реестре: неполный Lean-модуль не понижает
  бумажное доказательство и не повышает открытый claim.
- [ ] Шапка модуля — человеческим языком: что доказано, что
  НЕ доказано, гипотезы, пробелы, ссылка на численный тест.
  Шапок вида «TEST COPY ONLY» в пуше нет (прецедент: они
  чистились перед пушем, файлы пересобирались).
- [ ] Агрегатор: новый модуль импортирован в `Bgs.lean`
  в правильном месте (PhaseLemma после `LineDBridge`,
  149Props после `PhaseLemma`, M1 после `NAverageBridge`,
  Units после `M1` — для новых модулей место фиксируется
  здесь же, в §3, до начала работы). Проверка: модуль входит
  в транзитивное замыкание `lake build Bgs`, а не просто
  лежит на диске (ловушка §1).
- [ ] Diff пакета — только пакет: новые модули + импорты
  в `Bgs.lean` + точечные правки `formalization` в `claims.json`.
  Существующие модули моста не правятся (правило §2).
  После пуша — обратное чтение и сверка blob SHA всех файлов
  пакета; расхождение SHA — стоп и разбор, а не повторный пуш.
- [ ] CI: после обновления CI (по словам пользователя, «на днях»)
  полный прогон `lake build Bgs` на свежем HEAD-дереве —
  отдельный шаг после пакетных пересборок, а не их замена.

## 7. Плейбук сбоев

| Сбой | Первое действие | Запрещено |
|---|---|---|
| Недостающий olean после `lake env lean` | Пересобрать зависимость через `lake build`, потом повторить аудит | Считать это провалом теоремы |
| Модуль не виден в `lake build Bgs` | Проверить импорт в `Bgs.lean` и транзитивное замыкание (§1) | Считать проверку прямым запуском файла достаточной |
| `decide` / OOM / таймаут | Разбить модуль, доказать структурную лемму, вынести инстанс в отдельный файл | Повторить тот же запуск без изменений |
| Численный контрпример к формулировке | Остановить Lean-стадию, зафиксировать опровержение отдельным модулем, переформулировать | Подгонять константу или определение под контрпример |
| Недостающий аналитический вход (kickMatInf, J0) | Зафиксировать интерфейс с именованной гипотезой и списком недостающего | Подменять вход игрушечным объектом |
| HEAD ушёл во время подготовки пакета | Перебазировать пакет на свежую базу, пересобрать, пересверить SHA | Пушить на старую базу |
| Параллельный агент правит те же файлы (Line E) | Работать только в своей копии, сверяться с HEAD, пушить только свой пакет после разрешения | Править чужие файлы в main «по ходу» |

## 8. Что должно получиться на выходе каждой стадии

Не «модуль собран», а комплект: (1) модуль с человеческой шапкой,
(2) сохранённый лог `EXIT:0`, (3) полный список аксиом по всем
главным теоремам, (4) подсчёт `sorry`/`native_decide`/`decide`
с различением кода и комментариев, (5) список оставшихся гипотез
именами, (6) численный тест вне Lean (для стадий 2, 4, 5) или
явная пометка, почему он неприменим, (7) запись в реестр claims
только в статусе, соответствующем пунктам 3–5. Комплект без
любого из пунктов — неготовый пакет, и в main он не идёт.
